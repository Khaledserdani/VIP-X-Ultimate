# VIP X — Product Baseline

## Product
A free, standalone Android companion for user-authorized media playback: local images/videos, VIPXENC-encrypted local media, HTTPS/HLS/DASH streams, multi-stream previews, and floating playback surfaces. It must not modify or inject into other apps.

## Fixed user constraints
- 100% free: no subscriptions, paid APIs/services, paid backend, or required private server.
- Normal internet connectivity only (Wi-Fi or mobile data); no VPN requirement.
- No cloud builds or CI builds. Do not trigger GitHub Actions or another hosted build.
- Do not modify `main`, merge, or rebase without explicit approval.
- No root, app injection/modification, private token extraction, endpoint harvesting, or unauthorized DRM bypass.
- Protected playback is supported only through provider-authorized Widevine licensing and credentials.

## Implemented source code (not yet device/build verified)
- Arabic Jetpack Compose home screen, Live Grid screen, and Media Library screen. The manifest declares Android 13+ `POST_NOTIFICATIONS`; before opening playback-related screens, the home Activity requests this runtime permission when needed and continues into the feature even if the user denies it. Notification permission is not treated as a prerequisite for starting a media-playback foreground service; denial can limit normal notification-drawer visibility while Android retains its foreground-service task-manager disclosure.
- Media Library uses Android Storage Access Framework document pickers; it requests URI read permission for selected user files rather than broad storage access. It is registered as an Android share target for one or multiple images/videos (`ACTION_SEND` and `ACTION_SEND_MULTIPLE` with `image/*` or `video/*`). It validates each incoming `content://` URI and its MIME type, accepts up to 20 distinct items, and lets the user choose one item at a time for normal preview and floating display. When handing a shared item to the floating service, the URI is placed in `ClipData` with `FLAG_GRANT_READ_URI_PERMISSION` so Android can propagate the temporary read grant to the service. The share flow does not request broad storage access or inspect the sending app's private data.
- Local images are previewed with ImageView; local videos use Media3 ExoPlayer.
- `VipxEncryptedMedia` implements the app-owned VIPXENC container: AES-GCM authenticated chunks, PBKDF2-HMAC-SHA256 key derivation (310,000 iterations), random salt/nonce prefix, authenticated end marker in v2, and v1 read compatibility.
- Media Library accepts a user-selected VIPXENC file and password, decrypts it to app-private cache, and previews the recovered image/video. The temporary decrypted file is deleted when the Media Library Activity is destroyed.
- Unit-test source covers round-trip payloads, actual PNG and MP4 fixtures, wrong passwords, tampering, truncation, missing authenticated terminator, and trailing bytes. These tests have not been executed in this no-CI workflow.
- `PlaybackService` owns the single full-screen Media3 `ExoPlayer` through a `MediaSessionService`. It advertises a dedicated `إيقاف` media-button preference backed by the standard `Player.COMMAND_STOP`; after a standalone stop interaction, it clears the current media item and requests service shutdown; the bound service is destroyed after active controllers unbind, and its `onDestroy` path stops, clears, releases the player, and releases the MediaSession. Replacing a stream in `PlayerActivity` uses `clearMediaItems()` without sending the standalone STOP command, so replacing content does not trigger final service shutdown. The notification/controller UI decides which media-button preferences it can display, so the exact visual placement depends on the Android System UI.
- `MultiStreamPlaybackService` owns up to four Media3 ExoPlayer instances, exposes active stream URLs/player references, maintains one selected audible stream, and runs as a media-playback foreground service. The service promotes itself to foreground only after a real player has been added, so a restored protected stream waiting for fresh Authorization does not leave an empty playback notification. It notifies the Live Grid when audio selection changes or the selected stream is removed/failed, keeping the displayed audio status synchronized. Each preview player uses a bounded 12-second/12-MiB load-control target to reduce aggregate buffering pressure when four streams run together; this is a source-level resource limit, not a measured device-memory guarantee. Playback errors remove and release only the failed player, clear its audio selection if needed, and refresh the notification. The foreground notification includes an explicit `إيقاف الكل` action routed to `ACTION_STOP_ALL`; it clears the player map and audio selection, notifies the overlay to detach PlayerViews, releases every ExoPlayer, and removes the foreground notification. The foreground service stops when the last player is removed. Live Grid exposes its manual retry action for both asynchronous player errors and synchronous stream-start failures, while reusing only the current in-memory session Authorization. Its destroy path releases remaining players and removes its foreground notification. It also notifies the floating stream overlay whenever the active player set changes. On stream removal, failure, or stop-all, the overlay detaches its PlayerViews before the corresponding ExoPlayer instances are released; an empty overlay is removed immediately before its service stops. Newly added streams appear without requiring the overlay to be reopened. The floating stream overlay stops cleanly if binding fails or returns an invalid binder, and unregisters its listener and removes PlayerViews when disconnected or destroyed. If WindowManager rejects `addView` with `SecurityException` or `BadTokenException`, it also explicitly detaches every PlayerView created for that failed root before stopping, so failed attachment cannot leave player-to-view references behind.
- Live Grid preview visibility is now tracked separately from floating-overlay visibility. Grid `PlayerView`s register through grid-specific attach/detach methods, and `LiveGridActivity` marks the grid visible only while started; on stop/disconnect it marks the grid hidden. The playback service keeps muted previews running only when a floating overlay view exists or the grid is active with a registered grid view, while an explicitly selected audible stream may continue audio-only when it holds audio focus. This prevents a stopped Activity's still-composed AndroidViews from falsely keeping hidden previews active. This is a source-level lifecycle correction; background/overlay transitions still require target-device verification.
- `MultiStreamPlaybackService` now tracks every registered grid/overlay `PlayerView` per stream. Removing a stream, stopping all streams, a terminal player error, and service destruction synchronously detach registered views before releasing their `ExoPlayer`; Compose grid views and floating overlay views register/unregister through the service. This closes the gap where a Compose `AndroidView` could briefly retain a reference to a released player. Source-level checks do not replace runtime lifecycle testing.
- Android background-playback compatibility source review (targetSdk 35, minSdk 26): the manifest declares `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`; `MultiStreamPlaybackService`, `FloatingMediaOverlayService`, and `PlaybackService` all declare `foregroundServiceType="mediaPlayback"`. `POST_NOTIFICATIONS` is requested on Android 13+ before entering the grid/library/full player, but the pending navigation action is still invoked when permission is denied; denial therefore does not block playback. Floating overlay services verify `Settings.canDrawOverlays()` before adding `TYPE_APPLICATION_OVERLAY` windows, and video overlay promotion uses `startForegroundService()` on Android 8+. These are source/configuration checks only: notification drawer behavior, OEM background restrictions, overlay permission round-trips, PiP, and playback survival under process pressure have not been runtime-tested on Android 14/15/16 devices.
- Stream network/error behavior: preview players retain Media3's built-in load-error retry policy for retryable transient load failures; the service handles the terminal `onPlayerError` only after that policy reports failure, detaches views, and releases the failed player without interrupting other streams. The grid exposes a manual retry action rather than an unbounded custom retry loop, and now translates terminal network/timeout, HTTP, DRM, decoder, and manifest/parsing failures into actionable Arabic messages. Retry still depends on a valid source URL, reachable origin, and any required current authorization/license; no bypass or credential recovery is attempted.
- Multi-stream preview resource policy: each preview player now targets an 8 MiB LoadControl buffer (down from 12 MiB), with an 8-second maximum buffer, 1-second minimum/rebuffer thresholds, and no retained back buffer. Across four players this is a nominal 32 MiB combined target, not a hard memory cap; decoder surfaces, allocator behavior, and time-priority buffering can change actual use. The service pauses a muted stream when it has no registered grid/floating `PlayerView`, and resumes it when a view attaches. A selected stream continues audio-only when it has Android audio focus; transient focus loss mutes and pauses it if no view is visible, and focus gain resumes it. Thus visible floating previews continue in the background, while hidden muted streams do not keep consuming decode/network resources. Device battery, bandwidth, and memory impact still require real-device measurement.
- `MultiStreamPlaybackService` disables ExoPlayer-managed audio focus on the four preview players and arbitrates focus once for the single user-selected audible preview using Android `AudioFocusRequest`. Muted previews therefore do not compete with each other or the full player; focus loss mutes the selected preview, transient ducking lowers it, and focus gain restores the selected stream. Removing the selected stream, stopping all previews, or destroying the service abandons the focus request. If Android denies a focus request, the grid leaves all previews muted and shows a retry hint. Full-player and floating-video players retain Media3's normal audio-focus handling. These are source-level policies; actual device audio-focus behavior still needs handset testing.
- Live Grid can open a floating overlay for up to four streams already registered in VIP X. The overlay is movable and closable. It does not discover, inspect, or capture streams from other applications. In the Live Grid, the selected audio stream can be muted again without stopping video playback. Moving a stream to the full player removes its preview-grid entry and its session-only authorization from the grid state before launching the full player, avoiding a stale tile and duplicate decoding. The full player immediately removes the temporary Authorization extra from its launch Intent after reading it, then clears its local credential variable after constructing the in-memory Widevine request headers. Playback error UI reports the Media3 error code and a safe hint rather than exposing raw exception cause text; Live Grid also avoids displaying raw exception messages. The home-screen Authorization input state is cleared as soon as the launch request is prepared and when Widevine is disabled. The Live Grid also clears its Authorization input when Widevine is switched off. The full-player service is a single shared playback session: before a newly launched stream is installed, PlayerActivity clears the previous media item without sending the standalone STOP command, so the prior DRM media item is released without triggering final service shutdown. `MediaSessionService` retains background playback when playback is ongoing and applies its default task-removal handling; closing the Activity alone intentionally does not stop service-backed playback. The full-player MediaItem and its MediaSession player retain the request header in memory for the active protected playback session (including any provider-required license renewal); releasing/replacing the player session releases that media item and its DRM resources. Closing the Activity alone intentionally does not stop the service-backed playback. Media3 applies its normal load-error handling for retryable network failures; after a terminal player error, the service releases only that failed player, the preview clears its stale PlayerView reference, and the user can manually retry. The add-stream result message preserves an immediate playback-start failure instead of overwriting it with a success message.
- Media Library has a movable floating-media overlay action for a user-selected local image or video. It requests Android overlay permission when needed, displays images directly, and plays videos with Media3 in a media-playback foreground service. The service detaches PlayerView before releasing ExoPlayer, stops itself on asynchronous playback errors, and removes the media-playback foreground notification when a video is replaced by an image. While a video is active, its foreground notification exposes an `إغلاق الفيديو` action routed to `ACTION_CLOSE`, which stops the service and runs the normal overlay/player/file cleanup path. Incoming requests are validated before temporary-file ownership is accepted, so rejected requests do not prematurely delete a caller-owned decrypted preview.
- VIPXENC preview decryption now tracks a partially created destination cache file during the fallback copy path. If copying fails after the final destination was created, both the incomplete destination and the intermediate `.tmp` file are deleted; successful handoff keeps the existing ownership-transfer lifecycle unchanged.
- Process-death cache cleanup is best-effort: a newly created FloatingMediaOverlayService removes prior `vipx-floating-` cache copies because no previous service instance can still own them. MediaLibraryActivity prunes `vipx-dec-` preview files older than 24 hours on launch, avoiding deletion of recent files that could belong to another still-running Activity. Android may kill a process without calling `onDestroy`; cache cleanup therefore cannot be treated as immediate or guaranteed before the next relevant launch.
- For a decrypted VIPXENC preview held in a file URI, MediaLibraryActivity explicitly transfers temporary-file ownership to the floating-media service when service startup is accepted. The service copies the file into its own cache, attaches the overlay, and only then deletes the Activity-owned source; if attachment fails, service cleanup removes both temporary files. This avoids a race where Activity destruction could delete the source before the service had a chance to copy it. The service deletes its copied temporary file when the overlay closes or the service is destroyed.
- Full player uses Media3/MediaSessionService and has Picture-in-Picture configuration.
- HLS/DASH Media3 modules are included. This remains a URL-based playback app, not a general web browser or cross-app media discovery engine.

## Important limitations / next work
- Floating stream previews and floating local media are separate services. The local-media overlay displays one selected image or video at a time; it does not automatically discover media in another app.
- The Media Library's SAF URI grants are persisted where supported. Floating playback depends on the selected document remaining readable through its granted URI.
- Decrypted media is stored in Activity-managed cache and deleted when that Activity is destroyed; the floating-media service makes its own temporary copy before displaying a decrypted file URI.
- Android application sandboxing means an overlay permission does not grant access to another app's private media, memory, network requests, or DRM sessions. The current cross-app path is user-initiated sharing through Android `ACTION_SEND` or `ACTION_SEND_MULTIPLE` (up to 20 items); it does not enumerate an app's media or automatically detect live streams. Further integrations require an explicit supported share/provider/SDK/API flow.
- Widevine configuration exists, but no actual provider-authorized protected stream/license has been tested. Do not claim that arbitrary encrypted broadcasts can be opened.
- Four-player capacity is a configured ceiling, not proof every device can decode four simultaneous streams. Decoder, memory, bandwidth, battery, and thermal limits need target-device tests.
- The floating overlay, multi-stream service, local media viewer, and encryption implementation have not yet passed a recorded local Gradle build or target-device test.
- No APK install/device playback acceptance test is recorded.

## Acceptance gate
A feature is complete only after a successful local build and target-device test. Protected DRM playback is accepted only after a provider-authorized stream plays with a valid license. Multi-stream playback is accepted only after concurrent real streams run stably on the target device.

## Security testing boundary
Test encryption/decryption with app-owned files, keys, devices, and services, or with explicit authorization. VIPXENC is an app-owned file format; it does not unlock third-party DRM. Never imply universal decryption of arbitrary encrypted files.

## Excluded
Unauthorized DRM/access-control bypass, private endpoint/token extraction, app modification/injection, paid APIs/services, required backend hosting, cloud builds/CI, APK publishing/distribution, and claims of universal playback.
